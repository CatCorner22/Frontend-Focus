# Research record 13: the Fit check learns Floor A9 (target size)

Prepared 2026-11-19 by the builder, at the owner's direction to take the app's capabilities further toward the North Star (built output indistinguishable from advanced human work). Status: the owner has not reviewed this record. It supports 1 change only: the Fit check now checks the part of Floor A9 that a program can check. Nothing in this record calls a page "accessible", "WCAG compliant", or "ADA compliant" (hard rule 8).

## The gap this closes

I. Every Vision writes Floor A9 into section 7 when Contrast checks is "Fix for me": "Every pointer target is at least 24 by 24 CSS pixels, or has enough space around it that a 24 px circle on it touches no other target" (Catalog record A9, source WCAG 2.2, success criterion 2.5.8 Target Size (Minimum), AA, reviewed 2026-11-16).
II. No program checked any part of it. `plugin/fit/src/floors.ts` named a checked part for 33 of the 56 requirements; A9 was not among them, so a build could ship 16 pixel icon buttons in a tight row, pass the Fit check at status 0, and break the very promise its Vision made. A promise that no program verifies is the central failure mode of AI-built front ends: the page looks right and does not work right.
III. The Catalog's own "how a program checks it" note for A9 already prescribed the method, unbuilt: "Computed-style measure: bounding box of each link, button, and input; for boxes under 24 px, run the circle-spacing test from the Understanding page."

## What the sources say

I. WCAG 2.2 success criterion 2.5.8 (normative text, read on the W3C Understanding page, 2026-11-19): "The size of the target for pointer inputs is at least 24 by 24 CSS pixels", with exceptions. The exception this program applies is Spacing: "Undersized targets (those less than 24 by 24 CSS pixels) are positioned so that if a 24 CSS pixel diameter circle is centered on the bounding box of each, the circles do not intersect another target or the circle for another undersized target."
   A. Source: W3C, Understanding Success Criterion 2.5.8: Target Size (Minimum), https://w3c.github.io/wcag/understanding/target-size-minimum — read through search-result text and the project's own research record 12a (which read this Understanding page on 2026-11-16). Basis: search summary plus record 12a; not re-read in full on 2026-11-19. Grade: convention (a standard's own words), with that basis stated.
   B. The intent, in the Understanding page's words: "to help ensure targets can be easily activated without accidentally activating an adjacent target." The disabilities named are hand tremors, spasticity, and quadriplegia.
II. The higher bar, reported as information and never as a deviation: success criterion 2.5.5 Target Size (Enhanced), AAA, asks 44 by 44 CSS pixels with no spacing exception. Apple's Human Interface Guidelines and Material Design ask about 44 to 48 units for touch. The Fit check's receipt note reports, for each window width, how many drawn targets reach 44 by 44 pixels, so the owner can see the distance to careful human practice without the Floor failing a page that meets the standard it promised. This is the Floor Gate plus a first, small Ceiling reading, in 1 measure.
III. Why this matters for AI-built pages in particular (the interaction gap):
   A. WebGen-Bench, as recorded in the Luminous Cognitive UI skill's gap analysis (reference 11): general code agents pass 52.0% of superficial design validation checks and only 17.1% to 21.1% of functional interaction checks. I-WebGenBench (2026, read as its abstract through search on 2026-11-19): generated interfaces are "structurally complete" with "numerous interactive elements, but only a fraction of these respond to user actions", and the gap is in interaction logic, not rendering. TeleGen (EMNLP 2026 findings, read as its abstract and repository summary through search on 2026-11-19): generated apps "often appear plausible but fail during actual use", through missing event handlers, broken navigation, and state updates never reflected in the interface.
   B. Target size is the part of that gap a static browser measure can decide exactly: geometry, not judgment. It is therefore the right first interaction measure for a checker whose rule is "a program measures, a model judges, a person decides".

## What the program does, and what stays with a person

I. The program collects, in each reading, every drawn pointer target: a link with an href, a button, an input that is not hidden, a select, a textarea, a summary, and an element with role button, link, checkbox, radio, switch, tab, or menuitem. Disabled and invisible elements are not targets a person can use, and are not collected.
II. A target of at least 24 by 24 CSS pixels passes the size part. An undersized target passes only under the spacing test above: its 24 pixel circle, centered on its bounding box, must intersect no other target's bounding box and no other undersized target's circle.
III. The inline exception: a link drawn inline inside a block of text that holds more words than the link itself (a link inside a sentence) is not counted, as the standard excepts it. Whether the words around it are truly a sentence stays with a person.
IV. Stays with a person, and the checked-part words say so: the equivalent-control exception (another control on the page does the same thing at full size), the essential exception (the size is essential, as a point on a map), targets drawn by a script after the readings end, targets inside frames and closed shadow roots, and whether a target's size is right for its importance beyond 44 pixels.
V. The 44 by 44 reading is information in the Floors measure's note. It never changes the status, and it is never worded as a requirement the page failed.
